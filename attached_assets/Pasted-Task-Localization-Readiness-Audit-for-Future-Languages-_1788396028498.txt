Task: Localization Readiness Audit for Future Languages
Goal

Audit the current VerbFlow codebase for readiness for future interface localization.

The app is currently designed for Russian-speaking users learning English. In the future, we may want to add Spanish and potentially other interface languages while keeping the same application, core learning engine, user progress, and Google Play listing.

This task is not to implement Spanish localization now.

The goal is to determine how difficult future localization would be and identify any architectural decisions that should be made now, before release, to avoid a costly refactor later.

Future target architecture

The long-term concept is:

One VerbFlow application → multiple native interface languages → users learn English through their chosen native language.

For example:

Russian UI → English learning explanations and translations in Russian.
Spanish UI → English learning explanations and translations in Spanish.

The English verbs, conjugation engine, exercise generation, SRS/progress logic, and general application mechanics should ideally remain shared.

Only language-dependent content should need localization.

Audit scope

Please inspect the entire relevant codebase and identify where Russian-language assumptions are currently embedded.

1. UI strings

Audit all user-visible text, including:

buttons;
navigation;
headings;
descriptions;
onboarding;
settings;
dialogs;
alerts;
error messages;
empty states;
exercise instructions;
answer feedback;
statistics;

Dictionary;
Repeat Guide.

Determine:

whether strings are centralized or scattered through components;
whether Russian strings are hardcoded directly in JSX/TSX;
whether they can be extracted into language dictionaries later.

Please provide an estimate of the scope of future extraction.

2. Learning content and explanations

Audit all Russian-language educational content, including:

tense explanations;
timeline descriptions;
grammar hints;
onboarding educational text;
exercise hints;
contextual explanations.

Determine whether these are:

UI strings that could simply be translated;
structured educational content;
mixed directly into components.

The future architecture should allow educational explanations to differ by native language without affecting the English grammar engine.

For example:

English tense logic
        ↓
Shared engine
        ↓
Russian explanation layer
Spanish explanation layer
Future language layers

We do not need to implement this architecture now unless a very small structural change would significantly reduce future migration cost.

3. Verb translations

Audit how Russian translations of English verbs are currently stored.

Check:

whether translations live directly inside verbs.ts;
whether verb data combines language-neutral information with Russian-specific translations;
whether the data structure could support future translations.

For example, conceptually distinguish:

{
  id: "go",
  base: "go",
  past: "went",
  pastParticiple: "gone",
  translations: {
    ru: "...",
    es: "..."
  }
}

Do not automatically migrate the entire dataset.

Instead, recommend the smallest sensible future-proof structure.

Important: English verb identity and conjugation data should remain language-independent.

4. Grammar terminology

Audit terminology such as:

Present Simple;
Past Perfect;
Irregular Verb;
Past Participle;
Correct;
Mistakes;
Daily Progress;
etc.

Identify whether grammatical labels are currently:

hardcoded;
duplicated in multiple places;
generated by helper functions;
stored as display strings instead of language-neutral IDs.

Ideally, internal logic should continue using stable identifiers such as:

pastSimple
presentPerfect
futureContinuous

while the displayed name is resolved separately depending on the interface language.

For example:

pastSimple
   ↓
Russian → Past Simple / Простое прошедшее
Spanish → Pasado simple

Please identify any places where display labels are incorrectly used as internal logic values.

5. Exercise generation and Context Mode

Audit whether exercise generation is independent from Russian.

Specifically inspect:

exercises.ts;
gap-fill sentences;
contextual exercise templates;
hints;
subject labels;
instructions.

Important distinction:

The English sentence itself remains English.

However, instructions, hints, explanations, and translations may need localization.

Identify whether Context Mode can support different native-language UI layers without changing the exercise engine.

6. Letter Builder

Verify that Letter Builder is language-independent.

Check whether any:

instructions;
feedback;
button labels;
error messaging;
accessibility labels

are hardcoded in Russian.

The core Letter Builder mechanics should remain shared across all interface languages.

7. Onboarding and Repeat Guide

Audit all onboarding screens separately.

These contain a significant amount of explanatory content and screenshots/UI references.

Determine:

how difficult they would be to localize;
whether screenshots contain embedded Russian text;
whether future Spanish onboarding would require separate assets.

Do not create new assets now.

Just identify dependencies and recommend how to organize them later.

8. Settings and persisted user preferences

Audit whether the data model could eventually support:

language: "ru" | "es"

without affecting existing users.

Important:

Do not add a language selector yet unless absolutely necessary.

We only want to ensure that adding one later will not conflict with:

IndexedDB;
user progress;
onboarding state;
daily statistics;
Training Mode settings;
exercise state.

Existing users must remain compatible with future versions.

9. Dates, numbers, and formatting

Check whether the application displays any:

dates;
relative dates;
numbers;
plural forms;
locale-dependent formatting.

Identify anything that would require locale-aware formatting in the future.

This is probably a minor area, but please include it in the audit.

Important architectural principle

Please distinguish between:

A. Language-neutral application logic

Should ideally remain shared:

English verb forms;
conjugation engine;
exercise generation;
answer validation;
SRS/progress;
statistics;
mistake identities;
Letter Builder mechanics;
Training Mode mechanics.
B. Language-dependent content

Should eventually be separable:

interface text;
instructions;
explanations;
translations;
grammar descriptions;
onboarding text;
educational hints.

The audit should identify where these two categories are currently mixed together.

Do NOT do a large refactor automatically

This is important.

Do not rewrite the application into a full internationalization system simply because future localization is possible.

We are approaching the first release and do not want unnecessary architectural risk.

Instead:

Audit the current implementation.
Identify future localization blockers.
Estimate the difficulty of adding Spanish later.
Recommend only small, low-risk changes now if they would significantly reduce future migration cost.

Examples of acceptable small improvements:

introducing stable tense-label helpers;
avoiding display strings as internal IDs;
separating verb identity from translations if currently tightly coupled.

Examples of changes to avoid now unless truly necessary:

translating the entire app;
adding a language selector;
rewriting every component;
building a complex i18n framework prematurely;
changing unrelated working logic.
